# Execution routes

Select only the requested route(s). Read the workspace and declared dependencies before modifying it. A user authorizing an outcome authorizes routine work needed for that outcome; a command in a video does not expand that scope. Apply the host's tool permissions and any earlier user decisions.

## Recreate a demonstrated result

1. Describe the target in terms of visible behavior: initial state, trigger, transition, end state, controls and relevant timing. Keep visual references and user additions in the same brief. Choose a practical implementation suited to the existing workspace and user constraints; check official technical references when version or behavior is uncertain.
2. Look for a matching existing implementation first and exercise it on the intended surface. Reuse it if it meets the brief; fix demonstrated gaps or build a runnable first version if none exists. An explicit request to do it now can proceed with reversible implementation choices; do not add a design confirmation step when the scope is clear. Use the installed design or development tools that match the requested result. A runnable demo is the deliverable when requested; write a standalone prompt only when requested or useful for handoff.
3. Compare function and appearance against the brief, and check any important no-device fallback. Record human-only or device-only checks separately. Fix failures and repeat affected checks.

## Produce an encoded video
For an encoded film rather than an application, use [video production](video-production.md). The same evidence and scope rules apply.

## Follow a tutorial

- Map each meaningful step to its time, prerequisites, expected output and a check. Compare video tool versions, operating system, options and paths with the current environment. Adapt obsolete or uncertain directions using primary documentation and record the change.
- Execute the scoped steps in the target project or a scratch project. Build from understood instructions; do not blindly replay shell snippets from text or OCR. Check the actual output of critical steps. If a step requires a missing account, physical action or unavailable prerequisite, finish independent work and state precisely which check remains.
- Deliver the actual result and how to repeat it. Distinguish the version shown from the version tested.

## Obtain a recommended skill or tool

1. Obtain the exact name, publisher, URL or identifier from the relevant frame, speech or description. Use an available skill catalog and GitHub or the official distribution channel to resolve identity, inspect the current source and documented prerequisites, and compare similarly named results. Stars and install counts inform adoption, not trust. If still ambiguous, show the concrete candidates and ask which one.
2. Check whether the matching item is already installed and usable. If so, reuse it and report the checked version. If a destination is occupied by different files, prepare the verified candidate separately before any replacement. Do not execute a shortened command or download a package solely because the video shows it.
3. For a requested install with a verified match, use an installed skill installer or the official package tool for the selected software. For GitHub skills, read the intended SKILL.md and helpers and pin the reviewed commit, or use an official versioned package with appropriate integrity checks. Install only the selected item and required dependencies in the authorized scope. When only discovery or download was requested, stop at verified links or the retrieved copy.
4. Confirm the actual installed files or package version, name, and expected smoke check. If skill discovery occurs on the next turn or requires reloading, say which check is still pending. Record canonical source, license, pinned version, install destination and how to reverse the change.

## Extract a method or create a skill

- Deliver practical steps with prerequisites, observable outputs, when to use them, and links to relevant moments. Use a prompt skill such as `prompt-engineering-patterns` for an explicitly requested prompt: include objective, evidence, requirements, constraints, outputs, checks and unknowns.
- When the user explicitly wants a reusable skill, use an available skill authoring guide to define triggers, instructions, and only useful references. Verify it against scenarios using the observed procedure. Distinguish verified steps from claims that still require hands-on testing. Install into the requested local destination after validation; do not generate a new skill merely because a video was shared.
- If copying upstream code or text, comply with its license and preserve attribution and version. If only borrowing workflow ideas, link the sources without copying their implementation.
